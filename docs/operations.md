# Operations

Titan GraphQL is a pre-1.0 library and reference service. Production deployments use package-bound
database execution through the standalone HTTP frontend ZIP, with a reviewed model and its exact
generated Titan package. This document describes the supported operating boundary; it is not a
substitute for an organization's database, identity, backup, or incident-response controls.

## Deployment unit

Deploy these inputs together:

- the verified `titan-graphql-*-database-http-frontend.zip` distribution;
- the reviewed `titan.graphql.yaml`;
- the dialect-specific migrations generated by `titanPackage`;
- `titan-artifact.json`, the inventory/install-verification artifacts, and
  `titan-graphql-package.json` emitted by `titanGraphqlBindPackage`; and
- the matching generated database-frontend deployment descriptor.

The descriptor binds those immutable inputs to the frontend. Frontend startup fails before opening a
database connection when it is absent or malformed. The installed entry point verifies the model and
runtime identity before serving requests, so a package installed into the wrong database is rejected.

Use a database identity that can execute only the generated application routines it needs. Policy
booleans are compiled by the trusted application boundary and passed to those routines; arbitrary
SQL clients must not be able to call them as an authorization bypass. See [../SECURITY.md](../SECURITY.md).

## Runtime configuration

The relevant settings are:

| Setting | Production guidance |
| --- | --- |
| `TITAN_GRAPHQL_FRONTEND_DESCRIPTOR` | Required absolute path to the descriptor generated for the installed dialect/package. |
| `TITAN_GRAPHQL_JDBC_URL` | Required PostgreSQL or MySQL JDBC URL selected by the descriptor's dialect. |
| `TITAN_GRAPHQL_JDBC_USERNAME` / `TITAN_GRAPHQL_JDBC_PASSWORD` | Required database identity supplied through a secret manager; no credential is committed or accepted over HTTP. |
| `TITAN_GRAPHQL_HTTP_PORT` | Positive listener port; defaults to `8080`. |
| `TITAN_GRAPHQL_HTTP_MAX_BODY_BYTES` | Positive HTTP-body limit; defaults to `1048576`. |
| `TITAN_GRAPHQL_DATABASE_STATEMENT_TIMEOUT_SECONDS` | Positive database-statement ceiling for each whole-request invocation; defaults to `30`. A trusted per-request deadline may reduce it but cannot extend it. |
| `TITAN_GRAPHQL_HTTP_TRUST_REQUEST_CONTEXT_HEADERS` | Keep `false` unless an authenticated gateway removes client values and injects verified `X-Titan-*` context. |

Before installing a MySQL whole-request package, set `max_allowed_packet` to at least `16M` and
verify it with `SELECT @@max_allowed_packet`. Titan install verification preflights that setting
against the package's largest UTF-8 SQL statement plus a protocol reserve before it executes any
package SQL. The generated routine closure is larger than the legacy 1 MiB default; this
server-side deployment prerequisite is separate from the frontend's HTTP body limit.

`titan.graphql.execution.mode`, `quarkus.datasource.*`, management settings, and application-mutation
providers configure the root Quarkus compatibility application only. They are not settings for the
shipping frontend ZIP and are scheduled for removal or control-plane migration.

Optional application mutation providers are immutable runtime configuration. Their handlers own
domain transactions and idempotency; their audit sink must be durable when audit records are
required for observability. A sink must not throw. Correctness- or compliance-critical audit must be
committed by the handler with the domain change, normally through the same transaction or an outbox.
Duplicate/missing registrations fail runtime initialization.

Do not enable the frontend endpoint as a health check until the package, descriptor, binding,
migrations, and source schema are all present. An unavailable or unattested database returns an
error; there is no silent fallback to the Java engine.

## State and lifecycle

State is classified as follows:

- **Durable:** application/source rows and installed Titan routines in the serving database;
  management records when `titan.graphql.management.store=jdbc`; file-store data only for as long
  as its configured volume remains intact.
- **Reproducible release output:** generated carrier source, SQL migrations, inventory, install
  plan, verification report, rollback SQL, model binding, SDL, and introspection artifacts. Rebuild
  them from a pinned source revision, model, Titan submodules, JDK 21, and the declared dialects.
- **Build cache:** `.gradle/` and `build/`. They are ignored and may be discarded when no build is
  running.
- **Ephemeral process state:** parsed plans, request/relation batching state, and registered preview
  candidates. It disappears on restart and must not be used as a system of record.

The JDBC management store owns transaction, idempotency, and audit persistence through Titan's
GAP-006 store. The file store does not provide a multi-process coordination contract. Run a single
writer in file mode; use JDBC mode for restarts, multiple instances, or durable administrative
workflows.

## Rollout and rollback

Before rollout, run [verification.md](verification.md), back up the source database according to
its own operating policy, and retain both the new and previous release packages. Apply compatible
source-schema migrations first, install and verify the generated package, deploy its matching model
and binding, then admit traffic.

For rollback, stop admitting new requests, execute the generated dialect-specific rollback script
for the failed package when appropriate, restore or reinstall the previous verified package, and
deploy its matching application/model/binding as one unit. A binding from one release must never be
paired with another release's SQL. Validate attestation before restoring traffic.

Generated rollback SQL concerns Titan package objects; it is not a backup or reverse migration for
application data. Destructive source-schema rollback requires a separately reviewed data plan.

## Observability and incident response

Capture application logs, database errors, deployment fingerprints, artifact/model semantic hashes,
and install-verification reports in the deployment record. Do not log bearer tokens, datasource
credentials, raw trusted-context headers, or sensitive GraphQL variables. Treat repeated attestation,
binding, or unsupported-plan failures as deployment/model drift rather than retryable user errors.

On suspected credential disclosure, disable the administrative surface, rotate the affected secret
and database credential, inspect database audit evidence, and follow the private-reporting process in
[../SECURITY.md](../SECURITY.md).
