# Titan GraphQL Query Contract Conformance Matrix

Status: QC10 working matrix.

This matrix classifies the accepted query contract from `docs/query-contract.md` against the current generated demo-blog runtime. A feature is `ACCEPTED` only when Java-mode is the reference behavior, SQL-mode can lower or evaluate the same supported surface, and tests prove equivalence where execution behavior is involved.

Classifications:

- `ACCEPTED`: production-supported for the bounded demo surface.
- `JAVA_ONLY`: implemented in Java-mode but not production-supported because SQL-mode or transport equivalence is missing.
- `PENDING`: accepted contract target that is not implemented yet.
- `OUT_OF_SCOPE`: intentionally excluded from the current query-only roadmap.

## Evidence legs

Each row carries three evidence legs:

- **Current Evidence** (Java-mode reference): the 460-test Java-mode suite
  (`TitanGraphqlFunctionsTest` and friends), which executes the SQL kernel's entry points
  in-JVM and pins exact JSON behavior.
- **SQL-Mode Evidence** (live PostgreSQL, automated — completion plan W2): the
  `integrationTest` task deploys the real `titanPackage` migrations
  (`R__titan_010_runtime.sql` + `R__titan_020_routines.sql`) onto a Testcontainers
  PostgreSQL, applies the demo DDL and the Java-mode fixture rows, then executes the
  conformance corpus (`GraphqlSqlModeConformanceCorpus`) through the deployed
  `public.execute_graphql*` stored functions and compares both legs as canonical JSON via
  core's `EquivalenceOracle` (`GraphqlSqlModeEquivalenceIT`). The Docker-free guard
  `GraphqlSqlModeConformanceCoverageTest` fails the plain `test` task if any `ACCEPTED`
  row loses corpus coverage, so the SQL-Mode Evidence column cannot silently go stale.
- **MySQL Evidence** (live MySQL 8.4, automated — completion plan W5.2): the same corpus
  through the packaged MySQL migrations (`mysql/R__titan_010_runtime.sql` +
  `mysql/R__titan_020_routines.sql`) and the MySQL demo DDL
  (`ddl/mysql/titan_graphql_mysql.sql`), compared Java-vs-MySQL by the identical
  canonical-JSON method (`GraphqlSqlModeEquivalenceMySqlIT`). All 97 of 97 cases now compare
  strictly: core's B-10 fix (titan f9e3b43) makes MySQL render boolean routine values
  `true`/`false` in text/JSON output, so the 6 formerly boolean-divergent cases of the now
  resolved `TG-BLK-012` class rejoined the strict corpus. The `KNOWN_DIVERGENT_TG_BLK_012`
  allowlist is retired to `Set.of()` (the empty guard is kept so a returning boolean-parity
  regression fails strict comparison loudly), so the MySQL Evidence column cites strict
  canonical-JSON equivalence for every executable row.

Rows whose behavior cannot be SQL-executed say so explicitly in the SQL-Mode Evidence
column (today: only `QC10-MATRIX`, the documentation row itself). The two
`QC11-QUARKUS-*` transport rows are SQL-evidenced at the exact lowered entry-point call the
HTTP bridge delegates into; the HTTP negotiation layer above it is Java by design and
covered by `GraphqlHttpResourceQuarkusSmokeTest`.

**Database-leg status at titan HEAD (2026-06-13, after core's TG-BLK-011 and TG-BLK-012
fixes, honest): both dialects fully clean.**

- `TG-BLK-011` (identifier overflow) is **resolved** — titan 5649ebb applies
  `NamingRules.identifierMaxLength` to record/enum names. Verified recovery:
  `titanVerifyInstall` passes both dialects (postgresql 1452 objects verified / mysql
  1438, zero diagnostics), and the PostgreSQL corpus is back to **97/97 equivalent,
  0 divergences** on a live run against core HEAD — the SQL-Mode Evidence column cites
  green runs again, not a historical result.
- `TG-BLK-012` (MySQL boolean→JSON rendering) is **resolved** — core's B-10 fix
  (titan f9e3b43) makes MySQL render boolean routine values `true`/`false` in text/JSON
  output where it previously rendered `1`/`0`. The MySQL corpus is now **97/97 strictly
  equivalent, 0 divergences** on a live run against core HEAD: the 6 formerly-tracked
  cases — `QC4-ALIASES/connection-aliases`,
  `QC6-SORT-CURSOR/generated-order-with-relay-cursor`,
  `QC7-TOTAL-COUNT-RELATION/relation-total-count-with-page-info` and
  `/relation-after-cursor`, `QC9-CONTEXT-FILTER/visibility-cursor-window`, and
  `QC10-INTROSPECTION-DIRECTIVES/schema-directives` — all compare strictly equal and have
  rejoined the strict corpus. The `KNOWN_DIVERGENT_TG_BLK_012` allowlist in
  `GraphqlSqlModeEquivalenceMySqlIT` is retired to `Set.of()` (empty guard retained so a
  returning boolean-parity regression fails strict comparison loudly). No kernel workaround
  ever existed, so nothing needed reverting.

```bash
./gradlew integrationTest
```

The live database legs have surfaced four core transpiler defects so far, all registered in
`docs/titan-blocker-register.md`: `TG-BLK-006` (control-character char literals corrupted in
emitted SQL) and `TG-BLK-007` (unsupported `String.equalsIgnoreCase` silently emitted as a
nonexistent SQL function) — both fixed by core (titan e13b7b6) with the kernel workarounds
since reverted — `TG-BLK-011` (identifier overflow, fixed by core in titan 5649ebb,
recovery verified on both dialects), and `TG-BLK-012` (MySQL boolean→JSON rendering, fixed
by core in titan f9e3b43 — the MySQL leg is now 97/97 strictly equivalent). All four are
closed; no kernel workaround remains for any of them.
